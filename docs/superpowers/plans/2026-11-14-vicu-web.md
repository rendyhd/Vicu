# Vicu web: implementation plan

A version of Vicu that runs in a desktop browser and is hosted from a Docker container next to a
Vikunja server. Scope settled with the user on 2026-11-14. Desktop repo only: `vicu-android` is not
touched, and no cross-app rule or fixture changes.

Use case: a laptop where installing apps is not allowed.

Status: plan only. Nothing is built. Written on 2026-11-14 at `f3f38d8` and checked against the
code again on 2026-11-19 at `ae94e9b`, 19 commits later; section 12 lists what that changed. The
figures below are from the second date, on the `pro` branch. The effort figures in section 9 are
estimates.

---

## 1. Ground rules

These hold for every step and are the acceptance criteria for the whole project.

| Rule | What it means in code |
|---|---|
| **W1 The desktop app does not change** | Every refactor in phase 1 is behaviour-neutral for Electron. `npm run verify` and the harness waves pass before and after each step. |
| **W2 One interface, one copy of the rules** | The web version uses the same renderer and the same `src/shared` rules. It reaches everything else through `window.api`, exactly as today. No second implementation of a rule. |
| **W3 No server state** | The container holds no user data, no tokens and no sessions. It serves files and forwards `/api/` to Vikunja. Any number of people can use one container. |
| **W4 Same origin** | The page and the Vikunja API share one origin through the container's proxy. The 2.4.0 test server sent no CORS headers to another origin, and the session cookie depends on it (section 4). |
| **W5 Out means hidden** | A feature that is out of scope shows no button, menu entry, setting or shortcut on the web. Nothing is shown disabled, and nothing fails at a click. |
| **W6 Nothing from other sites** | The page loads no script, font or style from another site, and its CSP allows connections to its own origin only. |
| **W7 Chrome and Edge first** | Both are the engine Electron uses. Firefox and Safari are best effort and not part of acceptance. Desktop window sizes only. |
| **W8 Text goes in the catalog** | Every text the web version adds for a person is a key in `locales/en.json`, written by the rules in `CLAUDE.md`, Translations. The hardcoded-text check covers `src/core/` and `src/web/` too. |

## 2. Scope

### In

| Area | What |
|---|---|
| Lists | Inbox, Today, Upcoming, Anytime, Logbook, projects, sections, tags, search with filters |
| Tasks | Notes editor, subtasks, labels, repeat, attachments and the image viewer, duplicate, templates, quick-add parser |
| Organising | Custom lists (rules and saved-filter import), project categories, task order, week start, Review, guided sessions and the weekly review, both without suggestions |
| Plan | The Plan screen, time blocks, Plan my day without its assistant, your own Events, importing a calendar file |
| Routines | Routines, shared routines, history, routines on Today |
| Collaboration | Assignees, comments, files in comments, sharing |
| Pro | All four layers, without the assistant parts |
| Basics | Drag and drop, keyboard shortcuts, command palette, themes, row density, settings |
| Reminders | Task reminders, routine reminders and the evening planning nudge as browser notifications, while a Vicu tab is open |
| Sign-in | Password, OIDC, API token |
| Language | The app's text in the reader's language where a catalog has it, and the Language setting |

Two steps that live under `src/main/offline/` are not about being offline and stay: the check that
stops a repeating task being completed twice from two devices (`repeat-completion-step.ts`) and
keeping both versions of notes changed in two places (`notes-save-step.ts`).

### Out

| Feature | Decided by |
|---|---|
| The assistant: Ask, smart dictation, brain dump, suggestions, local speech, and making tasks from notes, PDFs and pictures | User |
| The offline queue ("you are already online"). A change that fails rolls back with a message | User |
| Connected calendars: links, CalDAV, Microsoft 365, Google ("plan with events is good enough") | User |
| Reminders while no Vicu tab is open (that needs a server holding each user's sign-in, against W3) | User |
| Phone and tablet layouts | User |
| Voice input | Proposal, not objected to |
| Quick Entry, Quick View, tray, global shortcuts, browser link, Obsidian, launch on startup, update check, the close-button choice, the app icon badge | Cannot exist in a browser |
| Mac calendars, classic Outlook, watching a calendar file | Cannot exist in a browser |
| Standalone mode | A web version always has a server |

Reminders were first left out and brought back on 2026-11-14 as browser notifications, with the
limit stated wherever the user meets them: they fire only while Vicu is open in this browser.
Setting a reminder on a task works either way, because it is Vikunja data and also fires on the
phone and desktop apps.

## 3. What the code looks like today

| Fact | Figure |
|---|---|
| Renderer | About 69,500 lines, no Electron or Node imports, no `process.` reads |
| `window.api` references in the renderer | 295 in 50 files, 154 of them in `src/renderer/lib/api.ts` |
| IPC channels (`handleTrusted`) | 225. About 95 are in scope; the rest belong to features that are out (ai 24, calendar 21, qe 14, qv 13, offline-queue 12, update 9, speech 8, notes 4, and smaller groups) |
| Main-process code the in-scope features pull in | 77 files, about 14,400 lines, plus 35 shared files (reminders, the Pro person handler and the calendar file reader counted in) |
| Of that, the offline queue | About 2,850 lines, not needed |
| Of that, sign-in (`src/main/auth/`) | About 2,700 lines, mostly replaced by a much smaller browser version |
| Electron use in what remains | `net.request`/`net.fetch` (API client), `BrowserWindow.getAllWindows()` to tell windows about a change (six services), `app.getPath('userData')` (config, carrier ids) |
| Node use in what remains | `crypto.randomUUID` (four services), `path.join`, `Buffer` in the API client |

So the code that must run in a browser is mostly free of Electron already. The dependencies are
three: sending an HTTP request, keeping a JSON document, and telling the page something changed.
Reminders add a fourth, showing a notification, and the language setting a fifth, asking which
languages the reader prefers.

## 4. How it runs

```
browser tab                                  container                 Vikunja
+-----------------------------------+        +----------------+        +--------+
| renderer (unchanged)              |        | static files   |        |        |
|   window.api                      |  GET   |                |        |        |
| web host (new, src/web)           | -----> | /             |        |        |
|   handlers  (shared with desktop) |        |                |        |        |
|   core      (shared with desktop) | /api/  | proxy  /api/ --+------> | API    |
|   platform: fetch, IndexedDB,     | -----> |                |        |        |
|             BroadcastChannel      |        +----------------+        +--------+
+-----------------------------------+
```

**The host.** `src/web/` builds a `window.api` object in the page before the renderer starts. It
runs the same handler code the Electron main process runs, against browser implementations of the
three dependencies. There is no worker and no server process: each tab has its own host.

**Several tabs.** Without the offline queue there is no single-writer problem left, only four
small ones, solved with the Web Locks API, a `BroadcastChannel` and notification tags:

| Problem | Answer |
|---|---|
| Vikunja's SQLite answers parallel writes with "database is locked" | `sendSerially` takes a lock named for the origin, so writes are serial across tabs too |
| The refresh token rotates: two tabs renewing at once would spend it twice | One lock around the renewal; the new JWT is handed to the other tabs over the channel |
| Two tabs syncing the same settings document | One lock per document around a sync; a tab that did not sync reloads its copy when told |
| Every open tab has its own reminder timers | Each notification carries a tag made of the reminder's task and time; the browser shows one notification per tag |

**Sign-in.** Measured against the 2.4.0 test server: a password login returns a JWT that lives
about 10 minutes and sets `vikunja_refresh_token` as an `HttpOnly`, `SameSite=Lax` cookie with
`Path=/api/v1/user/token/refresh`, 30 days.

| Method | On the web |
|---|---|
| Password (with TOTP) | `POST /api/v2/login`. The browser keeps the cookie itself; the JWT stays in memory only. Nothing secret is readable by script or written to storage. |
| Renewal | `POST /api/v1/user/token/refresh` (the cookie's path is v1; confirmed to answer 200). On a timer before expiry, on a 401 with code 11, and when the tab becomes visible again. |
| OIDC | A full-page redirect to the provider with `redirect_uri` set to the web app's own address, registered once at the provider, as for the desktop browser sign-in. The code comes back as a query string, the host posts it to Vikunja's callback endpoint with the same address, and from there it is the password case. |
| API token | Kept in `sessionStorage` (gone when the browser closes) unless "Remember on this browser" is ticked, then in IndexedDB. The form says where it is kept. |
| Backup token | Not created on the web. The desktop app makes a 365-day token to survive a lost session; on a laptop you do not control, a lost session should mean signing in again. |
| Sign out | Ends the server session, clears memory, the stored token and every stored copy of account data. |

**Storage.** A per-browser IndexedDB database holds what `userData` files hold today: the config
(device settings plus the local copies of the synced documents), the carrier ids and, optionally,
an API token. Main reads the config synchronously (`loadConfig()`), so the host loads it once
before the first render, keeps it in memory and writes through, which is how `JsonFileStore` works.
The renderer's saved query cache (`lib/query-persistence.ts`) is off on the web: lists of tasks
should not stay on a machine you do not control, and starting offline is not a goal.

**Failed requests.** A browser's `fetch` does not say why it failed: the page cannot tell a
refused connection from a bad certificate or from a request that was sent and then lost. The
desktop rules that rest on that difference (`isConnectionError`) only decide what may be queued,
and nothing is queued here. On the web:

| What happened | What the user reads |
|---|---|
| The browser reports being offline | Not connected; nothing was sent |
| A failure before the answer began | The server could not be reached. For a create: the task may exist, check before trying again |
| A failure while the answer arrived | `answerCutOffMessage`, as on the desktop |
| A 2xx or 4xx answer that is not JSON | "Not the API" (a sign-in page or a firewall), as on the desktop; never a sign-in prompt |

While requests fail this way a notice at the top of the page says changes cannot be saved. It has
the place the sync panel's queue has on the desktop.

**Language.** The host answers `get-language` with the `resolveLanguage` main uses, from
`config.language` and the browser's preferred languages, and sends `language-changed` when the
setting is saved. The catalogs load through `import.meta.glob`, which the web build has too. The
texts of the application menu and the tray are not used.

**Links and dropped files.** In Electron, `web-security.ts` keeps the window on the app's own
page. A browser does not, so the web host guards the page the same way. A link opens in a new tab
after `safeExternalUrl`, never in the app's tab, and `open-deep-link` does the same and refuses
`obsidian:`. A file dropped outside a drop target is ignored instead of replacing the app: today
the only page-wide drop handler belongs to the notes import, and it steps aside while the
assistant is off.

**Reminders.** The scheduling is the desktop's own: `task-reminders.ts` and
`routine-reminder-rules.ts` have no Electron imports and move to core unchanged (one timer per
reminder, a refresh every 15 minutes and when the tab becomes visible, the task read again when a
timer fires). Only the showing differs: `notifications.ts` uses Electron's `Notification`, the web
host the browser's.

| Case | Behaviour |
|---|---|
| Permission | Asked once, from the switch in Settings, never on page load. Needs HTTPS |
| A tab is open, in front or not | A system notification; a click brings the tab forward and opens the task |
| Background tabs | The browser slows their timers to about once a minute, which is within a reminder's precision |
| The laptop slept, or the browser put the tab to sleep | When the tab runs again, reminders that came due in the meantime are shown together in the page, once, not as late notifications |
| Permission refused, or switched off by policy | The reminder appears as a message in the page while it is visible; Settings says notifications are blocked |
| No tab open | Nothing fires. Settings says so and points to Vikunja's email reminders |

**The container.** One image: the static build and an nginx that forwards `/api/` to
`VIKUNJA_URL`. It sets the CSP and the other security headers, sends `index.html` uncached and the
hashed assets cached, allows uploads as large as Vikunja does, and passes the client's address on.
Because the cookie's path starts at `/api/`, the web app must own the root of its hostname; a
subpath of another site is not supported in the first version.

## 5. Code layout

| Folder | Holds | May import |
|---|---|---|
| `src/shared/` | Pure rules, as today | Siblings only |
| `src/core/` (new) | What main and the web host both run: API client, pagination, carriers, the synced-document loop and its three documents, saved filters, known user, project counts, the write gate, the two pre-send steps, reminder scheduling, the calendar file reader, the Pro person handler (`pro-people.ts`), the language answer, the config normalizer, the handler groups | `src/shared`, `ical.js`, the `Platform` interface. Never `electron` or a Node module |
| `src/main/` | Electron: windows, tray, shortcuts, the offline queue, the assistant, calendars, native helpers, the Electron `Platform` | Everything |
| `src/web/` (new) | The browser host: the browser `Platform`, sign-in, `window.api` | `src/core`, `src/shared`, DOM |
| `src/preload/` | `createApi(...)` over `ipcRenderer` | `src/shared` |

Three pieces make the sharing safe:

1. **One API factory.** `createApi({ invoke, on })` in `src/shared/` builds the whole `window.api`
   object. The preload passes `ipcRenderer.invoke` and `ipcRenderer.on`; the web host passes a
   local dispatcher. The two objects have the same shape by construction.
2. **One handler registry.** `ipc-handlers.ts` (1,521 lines) is split into groups. A portable
   group is `register(handle, deps)`: Electron passes `handleTrusted`, the web host passes a map.
   Handler bodies hold real logic (count invalidation, the write gate, change notices), so they
   must not exist twice.
3. **One `Platform` interface.** `http` (a request with an idle timeout and the same error
   sentences `error-classify.ts` reads), `store` (load and save a named JSON document),
   `broadcast` (tell every page), `notify` (show a reminder), `languages` (what the system or
   browser prefers), `randomId`. Two implementations, each tested against the same
   cases.

`src/core/` gets its own tsconfig with the DOM and ES libraries and no Node types, so the compiler
proves it uses no Node API, and it is also checked under `tsconfig.node.json`.

## 6. Guard tests

| Test | Fails when |
|---|---|
| `core-imports.test.ts` | A file under `src/core/` imports `electron`, a `node:` module or something from `src/main/` |
| `web-channels.test.ts` | A channel of the API factory is neither handled by the web host nor listed in `WEB_UNAVAILABLE` |
| `web-capabilities.test.ts` | A renderer file uses an unavailable `window.api` namespace without reading the capability that hides it |
| `platform-contract.test.ts` | The Electron and browser `Platform` answer one of the shared cases differently (timeouts, a body that is not JSON, an empty 2xx, error wording) |
| Existing suites | Anything moved to `src/core/` keeps its tests; they move with it |
| `hardcoded-text.test.ts` and `scripts/i18n.mjs` | Extended: `SCANNED` gains `src/core` and `src/web`, so new text there must be a catalog key. A file that moves is moved in `hardcoded-text-baseline.json` in the same commit |
| `response-error-listeners.test.ts` | Extended: it scans wherever the Electron transport lives after step 1.2 |

Capabilities are one object, `window.api.capabilities`, defined once in `src/shared/`: `host`
(`electron` or `web`), and one flag per feature that can be absent (`assistant`, `voice`,
`offlineQueue`, `calendars`, `quickWindows`, `browserLink`, `obsidian`,
`standalone`, `updates`, `windowControls`, `openFiles`, `badge`). `assistant` also hides making tasks from notes, and
`windowControls` the close-button choice and the tray. `platform` stays the operating system, so
the web host reads it from the browser to label shortcuts correctly.

## 8. Shortcuts in a browser

A browser keeps some keys for itself and a page cannot take them. The desktop menu also sends four
actions that have no menu on the web.

| Desktop | On the web |
|---|---|
| Ctrl+N new task (menu) | Cannot be taken from the browser. Needs another key, decided in step 3.2 |
| Ctrl+Shift+N new event on Plan | Cannot be taken (private window). Needs another key |
| Ctrl+R, F5 refresh the view | The browser reloads the page, which rereads everything. The palette's Refresh stays |
| Ctrl+P print the view | Taken by the page and handled in the app |
| Ctrl+, settings | Taken by the page |
| Ctrl+D duplicate, Ctrl+Shift+O Focus, Ctrl+Shift+M import, Ctrl+I inspector, Ctrl+Shift+F flag, Ctrl+Shift+C comments, Ctrl+Shift+9, 8 and 7 for the lists in notes | Can be taken by the page; each is checked in Chrome and Edge |

## 10. Testing

- **Unit:** the moved suites, the guard tests of section 6, and new suites for the browser
  `Platform` and the web sign-in against fakes.
- **Harness:** `scripts/ui-verify/web.mjs` runs the existing scenarios against the web build with
  `playwright-core` driving the installed Chrome or Edge. Scenarios already work on a page object;
  the ones that replace an Electron dialog or need an out-of-scope feature are marked desktop only.
  Acceptance is the baseline wave plus `collab`, `plan-screen`, `plan-my-day` without its model,
  `plan-events`, `calendar-import`, `guided` without suggestions, `routine-history` and the three
  Pro scenarios. Added by the check of 2026-11-19: `language`, `pro-dollar-person`,
  `attachment-viewer`, `notes-links` and `keyboard-reorder`. The web profiles pin the language to
  English, as the desktop ones do, because scenarios find things by their English text.
- **Two tabs:** one scenario opens two pages on one profile: a bulk change in one while the other
  renews its session, then a settings change in one that the other shows.
- **Reminders:** the moved fake-timer suites, plus one scenario with the notification permission
  granted and the browser's `Notification` recorded: a reminder due in a minute shows once with
  two tabs open, its click opens the task, and with the permission refused it appears in the page.
- **Container:** a smoke test that starts the image against the test server and signs in.

## 13. As built (2026-11-20)

The plan was built on branch `web`. Where the build differs from the sections above, this section
is what the code does; `CLAUDE.md`, "Web version", is the description to keep current.

**No `src/core/` folder (sections 5 and 6).** Moving some seventy files would have touched every
import in the main process for no change in behaviour. Instead the code stays where it is and what
differs between the two hosts goes through a **host seam**: the alias `@host/<name>` resolves to
`src/main/host/<name>.ts` in the desktop build, the tests and `tsconfig.node.json`, and to
`src/web/host/<name>.ts` in the web build (`vite.web.config.ts`, `tsconfig.webhost.json`). The seam
modules are `http`, `windows`, `auth`, `env`, `storage`, `serial` and `notify`; there is no single
`Platform` object. "May not need Electron or Node" is enforced on what the web entry actually pulls
in, not on a folder:

| Planned | Built |
|---|---|
| `core-imports.test.ts` | `src/web/__tests__/portable-closure.test.ts` over `scripts/portable-closure.mjs` (the import closure of `src/web/main.ts` has no `electron`, no Node built-in, no `process` or `Buffer`; every seam module has both sides with the same exports), plus the web host's own typecheck without Node types (`tsconfig.webhost.json`, part of `npm run typecheck`) |
| `web-channels.test.ts` with `WEB_UNAVAILABLE` | `src/web/__tests__/web-channels.test.ts`: the channels left out are grouped by the capability that hides their callers |
| `web-capabilities.test.ts` | `src/renderer/lib/__tests__/web-capabilities.test.ts`, as planned |
| `platform-contract.test.ts` | `src/web/__tests__/http.test.ts` runs the web transport against a local server; both transports read answers with the same `src/main/api-answers.ts`, which keeps its desktop tests |

**Phase 0 was not a separate spike.** The first browser run of the real web build did its job.

**Capabilities** gained `serverChoice`, `secretStorage` and `deepLinks` next to the flags listed in
section 6.

**A new version (step 4.x, "reload notice").** There is no notice. The page is never cached, built
files carry a content hash, and a tab left open reloads itself once when a part it needs is gone
(`vite:preloadError`, `src/web/guards.ts`).

**Shortcuts (section 8).** New task is Alt+N and New event Alt+Shift+N in a browser; Ctrl+T has no
replacement ("!" sets a task due today everywhere). The application menu's shortcuts (New task,
Print, Settings) are sent to the page by `src/web/shortcuts.ts`.

**Publishing.** `.github/workflows/web-image.yml` builds and checks the image on pushes to `main`
and publishes to `ghcr.io` only from a manual run with "publish" ticked. Nothing has been published.

**Verification.** `node scripts/ui-verify/web.mjs` drives a real browser against the built page,
served the way the container serves it, with the seeded local Vikunja.
