# Vicu Pro: implementation plan

Source: the proposal page "Vicu Pro" (https://claude.ai/artifact/KaaqEviqrR7GcrVo8TZYhP), with all 33
decisions settled on 2026-11-11. Both repos: `vicu` (desktop) and `vicu-android` (Android and iOS, one
shared Compose module). This plan covers everything in the proposal, end to end: server checks, the
cross-app contract, the shared rules, desktop, mobile, tests, harness and release.

Pro ships as one feature set. It is built in the order below, merged to `main` continuously, and kept
behind a hidden developer switch until the last step turns it on for users.

---

## 1. Ground rules

These hold for every step and are the acceptance criteria for the whole project.

| Rule | What it means in code |
|---|---|
| **O1 Off is today's Vicu** | With `pro_enabled` off, every list, count, card, parser result, Quick Entry, Quick View, reminder and Plan screen is byte-for-byte what the release before Pro produced. Proven by the `pro-off-parity` harness scenario and the parser corpus run with Pro off. |
| **O2 Off deletes nothing** | Turning Pro off never writes. Pro data stays on the server and in the ledger. |
| **O3 Pro only adds** | Pro writes only: `is_favorite`, a lone `start_date`, `blocked`/`blocking` relations, new synced-pref keys, a new synced document (the ledger), new custom-list filter keys, device config. Never description markers in task or project notes, never due dates, positions or sort orders on its own initiative. |
| **O4 Others keep Pro data safe** | Phones, older versions and Vikunja's web app edit Pro tasks without losing Pro data. Merge patches send changed fields only; unknown synced-pref keys, list keys and documents are kept; a lone `start_date` survives due-date edits. |
| **O5 Unknown shows more** | A version that cannot read a Pro list condition shows every match. |
| **Contract first** | Every rule both apps read is written in `docs/cross-app-semantics-v1.md` and its vectors before code, in both repos, byte-identical. The fixture wins over prose. |
| **Both repos** | Every shared rule has a TypeScript and a Kotlin implementation run against the same vectors, in three zones (Pacific/Auckland, America/New_York, Europe/Amsterdam on mobile). |
| **Standalone mode** | Pro is unavailable in standalone mode (no server), like the planner. |
| **Hidden until done** | `VICU_PRO_DEV=1` (desktop env) and a debug-only toggle (mobile) show the Pro settings page while building. The real switch appears in the release step. |

## 3. Verify on the server first (M0)

Run against the Docker Vikunja 2.4.0 test server (`vicu-test-vikunja`) with two users. Record the
answers at the top of the contract section, like the collaboration plan did. A different answer
changes the design where noted.

| Check | Expected | If not |
|---|---|---|
| `PATCH /tasks/{id}` with `{ "is_favorite": true }` sets the favourite for the caller only; a second user sees `false`. | Per user (API docs say so). | Flags become a synced pref (decision 22 B). |
| Does setting `is_favorite` move `updated`? | Probably not (separate table). | Document it; the "Changed" list condition ignores flags. |
| A task with `start_date` and no `end_date` round-trips; `start_date` alone is accepted by merge patch and cleared by `null`. | Yes. | Fall back to decision 21 B. |
| Completing a repeating task moves `start_date` alone (no `end_date`) by the interval, for `repeat_mode` 0, 1 and 2. | Contract 16 says start and end move together; check start alone. | Pro moves the start itself after completion. |
| `PUT /tasks/{id}/relations` with `blocked` creates the inverse `blocking` on the other task; cross-project works; a related task in a project the caller cannot see. | Yes; check visibility. | Hide "after" targets the user cannot read. |
| `related_tasks.blocked[]` entries in collection responses carry `done`. | Yes (they carry task objects). | Fetch blockers by id in one batch. |
| Deleting a task removes its relations. | Yes. | Clean up on delete. |
| Filter syntax `start_date < now \|\| start_date = null` with `filter_include_nulls`. | Works. | Availability stays client-side (it is anyway). |
| Largest description a carrier can hold on SQLite, Postgres and MySQL. Vicu caps writes at 384 KB (`HIDDEN_TASK_WRITE_MAX_BYTES`). | 384 KB fits; MySQL `TEXT` may cap at 64 KB. | Ledger archive threshold lowered; document a MySQL limit. |
| Seed 3,000 `estimate.<taskId>` keys into the synced preferences and time a full sync on desktop and phone. | Under 1 s, carrier under 200 KB. | Decision 25 goes to C (block length only). |

**Results (2026-11-12, Vikunja 2.4.0, `scripts/ui-verify/tools/pro-server-checks.mjs`):**

| Check | Result | Consequence |
|---|---|---|
| Favourite by merge patch, per user | Yes; the other user sees `false`; present in collection responses. | Decision 22 A stands. |
| Favourite moves `updated` | **Yes.** | Flagging counts as a change for the "Changed" list condition; documented in 21.4. |
| Lone `start_date` | Stored with `end_date` at the null date; survives a due-date patch; `null` clears it. | Decision 21 A stands. |
| Repeats move a lone start | Yes for modes 0, 1 and 2 (mode 2 from the completion time). | No Vicu code for repeating start dates. |
| `blocked` relation | Creates the inverse `blocking`; entries carry `done`; present in collection responses; deleting a task removes it. | No extra fetches. |
| Same relation twice | 409, code 4008. | Replay treats 409 as done. |
| Removing a missing relation | 404. | Replay treats 404 as done. |
| Server filter on `start_date` with nulls | 400. | Availability stays on the device (as planned); no server clause. |
| Description size (SQLite) | 512 KB stored intact. | The 384 KB write cap is the limit, not the server. MySQL unchecked. |
| Estimates as synced-pref keys | Each entry carries a full revision (UUID device id): about 150 bytes encoded; 2,000 entries pass the 384 KB cap. | **Decision 25 resolved:** estimates live in the ledger as a compact map `estimates: { "<taskId>": [minutes, wall_time_s] }` (about 30 bytes each; newer time wins), pruned when a task is done or gone. No `estimate.<taskId>` pref key. |

Also in M0 (user): run the Copilot prompt on three real meetings and one mail thread in the
employer tenant, anonymise the outputs, and add them as import fixtures (section 9.8).

## 4. Data model

### 4.1 Vikunja fields

| Field | Use | Notes |
|---|---|---|
| `is_favorite` (task) | Flag | Writable already (`TASK_WRITABLE_FIELDS`); never sent unless changed. |
| `start_date` without a block | Start date ("starts monday") | A block is `isTimeBlock(start, end)`. Everything else that reads `start_date` must go through `blockOf` (section 8). |
| `blocked` / `blocking` relations | "After" | Read from `related_tasks`; written with `PUT/DELETE /tasks/{id}/relations`; queued offline (decision 24). |
| `repeat_after`, `repeat_mode` | Unchanged; Pro adds an end rule beside it | Completion stays `{ "done": true }` only. |
| Project description | Free prose about an initiative | Never parsed by Pro; the review footer stays the last block. |

### 4.2 Synced preference keys (contract 11.3 registry)

| Key | Value | Written by | Pruned |
|---|---|---|---|
| `pro.area` | `["<categoryId>", ...]` | Settings, Pro | never (null resets) |
| `project_mode.<projectId>` | `"sequential"` or `"single"` (parallel = absent) | Project menu | when the project is deleted (Pro device) |
| `project_status.<projectId>` | `"on_hold"` | Project menu, review | same |
| `label_status.<labelId>` | `"on_hold"` | Label menu | when the label is deleted |
| `label_kind.<labelId>` | `"person"` | Label menu, import, capture | same |
| `repeat_rule.<taskId>` | `{ "until"?: "YYYY-MM-DD", "count"?: n, "catch_up"?: true }` | Repeat popover | when the task is done without repeat, or deleted |

Each key: a clause in `isWritablePref` (`src/main/synced-preferences.ts`), a key builder and reader in
`src/shared/synced-prefs.ts`, the registry in contract 11.3, and on mobile a constant in
`domain/model/SyncedPrefs.kt` with a small wrapper class like `PlannerPreferences.kt`. Pruning is done
by Pro devices only, after a refresh confirms the task or project is gone or done (null tombstones,
pruned after 90 days by the existing rules).

### 4.3 The Pro ledger (synced document, decision 27)

One hidden carrier per account, on the generic synced-document loop (desktop
`createSyncedDocumentService`, mobile `SyncedDocumentSync` with a `SyncedDocumentCodec`).

- Title: `Vicu Pro ledger (sync metadata — do not delete)`. Marker `<!-- vicu-pro:v1:<base64url JSON> -->`,
  search `vicu-pro`. Hidden by the existing rule on every version (`vicu-` prefix), owned by
  `created_by`, created only when there is something to keep.
- Records are `{ value, revision }` like synced prefs (`SyncRevision`); a `null` value is a tombstone.
  Unknown fields are kept at every level.

```jsonc
{
  "v": 1,
  "promises": {
    "<taskId>": { "value": {
      "dir": "theirs",                      // "theirs" (to you) or "mine" (you owe them)
      "person": 42,                         // label id of a person
      "words": "I'll have it signed off ...",
      "done_when": "Sign-off email from all three leads",
      "initiative": 17,                     // project id, optional
      "needs": [1203],                      // task ids of your promises it waits on
      "sent": ["2026-11-12T15:02:00Z"],
      "verdicts": [
        { "id": "v8k2", "at": "2026-11-12T14:40:00Z", "kind": "renegotiated",
          "new_due": "2026-11-27", "blocker": "Finance lead on leave" }
      ]
    }, "revision": { "wall_time_ms": 0, "counter": 0, "device_id": "" } }
  },
  "initiatives": { "<projectId>": { "value": {
      "rank": 3, "status": "active",        // active | parked | closed
      "sponsor": 51, "owner": 44,
      "ready": { "why": "...", "done_looks_like": "...", "smallest": "...", "not_doing": "...",
                 "decision_rights": null, "capacity": { "by": 51, "on": "2026-11-10" },
                 "stop_if": "No pilot region by 2027-01-15" },
      "parked": { "on": "2026-10-02", "reason": "after the data strategy lands" },
      "log_anyway": 1
  } } },
  "log": { "<id>": { "value": {
      "initiative": 17, "kind": "decision",   // decision | value | unknown
      "text": "Simple claims only for the pilot", "by": 51, "at": "2026-11-03",
      "ask": 45, "task": 1301, "resolved": null
  } } },
  "owed": { "<id>": { "value": { "what": "Pilot region: North or Central", "from": 51,
      "initiative": 17, "opened": "2026-11-03", "resolved": null } } },
  "escalations": { "<id>": { "value": { "promise": 1188, "a": 1188, "b": 1240,
      "status": "drafted", "draft": "...", "decision": null } } },
  "meetings": { "<id>": { "value": { "name": "Data steering", "people": [44, 45, 46],
      "initiatives": [17, 18], "rhythm": "weekly:thu" } } },
  "rounds": { "<id>": { "value": { "meeting": "<id>", "at": "2026-11-12",
      "discussed": [44], "skipped": [], "absent": [46], "not_discussed": [47] } } },
  "people": { "<labelId>": { "value": { "aliases": ["Jan de Vries"] } } },
  "estimates": { "1203": [45, 1794421060] },   // minutes, wall time in seconds; newer wins
  "settings": { "value": { "cap": 4, "cap_agreed": { "by": 51, "on": "2026-11-03" },
      "rule_agreed_on": "2026-11-03", "threshold": 2 } }
}
```

Merge (pure, both apps): newer revision wins per record, except `verdicts` and `sent`, which are
unions by `id` / timestamp, so two devices giving verdicts never lose one. Misses are counted from
`verdicts` (kind `not_yet`), never stored, so Undo (a verdict tombstone) and reopening stay correct.

Size: the write cap is 384 KB of description, and base64url costs a third, so about 280 KB of JSON.
Budget about 350 bytes per promise with history. Records closed for more than 180 days (a final
verdict, a resolved log entry, a resolved escalation, a past round) move to archive parts
`vicu-pro-archive:v1:<quarter>`, written and read on demand like routine archive parts
(`ROUTINE_ARCHIVE_SEARCH` pattern). The person page needs 90 days and never reads the archive; the
quarterly summary does. The service warns in the sync status when the main carrier passes 70 percent.

### 4.5 Custom-list filter keys (contract 3)

`availability` (`available` | `remaining` | `all`), `flagged` (`true` | `false`), `estimate_max`
(minutes), `project_status` (`active` | `on_hold` | `any`), `group_by` (`project` | `label` | `person`
| `due` | `start` | `flagged` | `none`), `row_fields` (array of `project`, `labels`, `due`, `start`,
`estimate`, `flag`, `notes`), `promise` (`theirs` | `mine` | `any`), `person` (label ids).

Written only when set (like `assigned`). Evaluated by every version that knows them, Pro on or off
(decision 23). Older versions keep them (`unknownFields` on desktop, `CustomListSync.unknown` on
mobile) and show more (O5). The server filter stays a superset: availability, flags, estimates and
promise conditions are client-side only.

### 4.6 Offline queue actions (decision 24)

New action types `add-relation` and `remove-relation` with `{ taskId, otherTaskId, kind }`.

- Desktop: `src/main/offline/types.ts`, `queue-parse.ts`, `queue-merge.ts` (an add and a remove of
  the same pair cancel), `queue.ts` (`enqueueAddRelation`), `task-writes.ts`, `replay.ts` (a
  `sendAction` case), `sync.ts` (through `sendSerially`), `summary.ts`, `classify.ts`, and
  `src/shared/offline-queue-types.ts`. `remapTempId` gains `otherTaskId`; a relation whose other task
  failed to create goes to the failed log as `dependency-failed`.
- Mobile: a new `entityType = "relation"` in `pending_actions`, a replay branch in
  `worker/SyncEngine.kt`, temp-id remap for both ids in `remapPendingDependents`, merge in
  `QueueMerge.kt`. `TaskRepositoryImpl.createRelation/deleteRelation` go through the queue.

### 4.7 Import format `vicu-import/1`

```json
{ "format": "vicu-import/1",
  "source": { "kind": "meeting|mail|chat", "title": "...", "date": "YYYY-MM-DD" },
  "items": [ { "type": "promise|action|update|open_item|decision|decision_needed|value", ... } ] }
```

| type | fields | becomes |
|---|---|---|
| `promise` | `owner`, `what`, `due?`, `initiative?`, `in_their_words?`, `done_when?`, `needs?[]` | Their promise; without `in_their_words` (no clear yes) your task "Confirm with <owner>: <what>" (decision 31). |
| `action` | `owner: "me"`, `what`, `due?`, `for?`, `initiative?` | Your task; with `for`, also `mine` in the ledger and linked as a need. |
| `update` | `id` (`t-<taskId>`) or `owner`+`about`, `status` (`delivered`, `late`, `not_yet`, `renegotiated`, `dropped`), `new_due?`, `blocker?` | A proposed verdict. |
| `open_item` | `what`, `ask?`, `initiative?` | Log entry `unknown` plus an "ask them" task. |
| `decision` | `what`, `by?`, `initiative?`, `date?` | Log entry `decision`. |
| `decision_needed` | `what`, `from?`, `initiative?` | `owed` record. |
| `value` | `what`, `where?`, `initiative?` | Log entry `value`. |

Reading rules (vectors in 9.8): take the text between the outermost `{` and `}`; strip code fences;
allow trailing commas; dates as ISO or words, read with the quick-add date rules relative to
`source.date`; unknown `type` or fields are reported, never fatal. Matching: people by label title,
then remembered aliases, then a unique first name; initiatives by project title inside the area;
updates by id, else by person plus wording (token overlap at least 0.6), marked "check".
