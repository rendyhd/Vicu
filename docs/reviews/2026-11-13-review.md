# Vicu desktop + mobile: review of 2026-11-13

Scope: `vicu` (desktop, branch `pro`, 2.8.0, Electron 44.5.1) and `vicu-android` (Android and
iOS, branch `pro`, HEAD 0203c51). Two parts: first the status of every item from the
2026-10-06 review, then a new pass on what an attacker could reach (UI layer, other people's
text on shared projects, stored passwords and tokens, the browser extension, Obsidian, the
update checker, the AI and voice features) and on API connectivity and lost updates between
devices. This is a report only; no code was changed and nothing was committed.

Severity, same scale as October: **P0** act now, **P1** security exposure with a realistic
path or likely data loss, **P2** real impact, **P3** minor. IDs: `S-*` security, `C-*`
connectivity and sync, `E-*` experience and consistency.

## 4. What an attacker could reach

### 4.1 Findings

**S-1 (P1, both apps) A shared task can make the Obsidian icon run any `obsidian://` address.**
Verified. **Fixed in the working tree on 2026-11-13** (not committed): the rule is in
`docs/description-format-v1.md` ("Task links") with the `noteLinks` vectors, `src/shared/note-links.ts`
and `util/NoteLinks.kt` apply it where the icon is drawn and again where the address is opened,
and `obsidian:` is no longer on the general link allowlist. Harness: `note-link-shapes`.
- Evidence: `src/renderer/lib/note-link.ts:13` takes whatever follows `<!-- notelink:obsidian://`
  in a task's notes. `TaskLinkIcon.tsx:14` and `quick-view/viewer.ts:256` hand it to
  `open-deep-link` on one click, `src/main/ipc-handlers.ts:1231` checks only the scheme, and
  `web-security-policy.ts:24` allows all of `obsidian:`. Mobile does the same:
  `util/TaskLinkParser.kt:21` and `ui/components/task/TaskLinkIcons.kt:120`.
- Scenario: someone with write access to a project you share (through Vikunja's web UI or the
  API, both keep HTML comments) adds the marker and a normal-looking note name to a task. You
  see the usual purple icon, titled "Open "Meeting notes" in Obsidian", and click it. Obsidian
  acts on the address. With the Advanced URI plugin, which Vicu's own uid links need, an
  address can run any command, including ones from a shell-commands plugin, and can overwrite
  files in the vault. Core Obsidian alone can create notes. No vault name is needed.
- Fix: in main (and in `TaskLinkParser`), accept only the two shapes Vicu writes:
  `obsidian://open` with only `vault` and `file`, and `obsidian://advanced-uri` with only
  `vault` and `uid`. Drop `obsidian:` from the general allowlist used by navigation and
  window-open. Put the rule in the description-format contract with vectors.

**S-2 (P2, Android) Browser sign-in can be intercepted by another app.** Verified in code; the
attack itself was not run.
- Evidence: `AndroidManifest.xml:85-97` catches the redirect on the custom scheme
  `com.rendyhd.vicu`, which any app may also register. `auth/OidcHandler.kt:52-57` sends no
  PKCE challenge (Vikunja does the exchange and does not pass a verifier on), and the exchange
  endpoint is public.
- Scenario: a malicious app on the phone registers the same scheme, receives the sign-in code
  and posts it to your Vikunja itself. It gets a session as you. The `state` check does not
  help: it only stops redirects Vicu did not ask for. iOS is not affected (the system binds the
  redirect to the session). The in-app window sign-in is not affected either.
- Fix: use a verified https App Link as the redirect, or ask Vikunja upstream to carry PKCE.
  Until then, say in Setup that browser sign-in is for passkeys and name the limit in the docs.

**S-3 (P2, desktop) Attachments lose the "came from the internet" mark, and the blocklist has
gaps.** Verified.
- Evidence: `src/main/ipc-handlers.ts:1127-1146` and `src/main/attachment-save.ts` write the
  server's bytes with no `Zone.Identifier` (Windows) or `com.apple.quarantine` (macOS).
  `src/main/attachment-safety.ts:13-39` does not list `.doc`, `.xls`, `.ppt`, `.xlsb`, `.rtf`,
  `.mht`, `.appinstaller`, `.theme`, `.search-ms`, `.zip` (macOS), `.fileloc`, `.inetloc`.
- Scenario: a collaborator attaches a file. A blocked `.exe` is not opened but is shown in
  Explorer without the mark, so a double click runs it with no SmartScreen question. An old
  `.doc` opens outside Protected View. On macOS an unpacked `.zip` gives an app that skips
  Gatekeeper.
- Fix: set the mark after writing, for Open and for Save, and extend the list.

**S-4 (P2, macOS) The signed app can be run as plain Node by any local process.** Verified in
the build files; not run.
- Evidence: `electron-builder.yml` sets no Electron fuses; `build/entitlements.mac.plist` has
  `disable-library-validation`, Apple events, audio input and calendars; the browser bridge
  depends on `ELECTRON_RUN_AS_NODE` (`src/main/browser-host-wrapper.ts:57`).
- Scenario: code already running as you starts `Vicu.app` with `ELECTRON_RUN_AS_NODE=1`. macOS
  counts it as Vicu, so it reads your calendars and uses the microphone without a new question.
- Fix: ship the bridge as its own small signed helper, then turn off `RunAsNode`,
  `EnableNodeOptionsEnvironmentVariable` and `EnableNodeCliInspectArguments` and turn on asar
  integrity.

**S-5 (P3 after a second look, both) Hidden-task markers are not tied to their author.**
Verified on desktop; the rule is the shared contract (section 10), so mobile is the same.
*Correction, same day:* scenario (a) is weaker than first rated. Someone with write access to a
shared project can already complete or delete any task in it; a marker only makes that quieter.
Tying the rule to the author would not help either, because the marker can be added to a task
you created. So the hiding rule stays as it is; (b) and (c) are the parts worth fixing.
- Evidence: `src/shared/hidden-tasks.ts:17` hides every task whose notes hold `<!-- vicu-x:`,
  whoever wrote it. Carriers are trusted only when `created_by` is you, which is right, but
  they are created in the Inbox.
- Scenarios: (a) a collaborator adds a marker to any task in a shared project and it vanishes
  from every Vicu user's lists, counts, search and reminders while staying open on the server.
  (b) If you share your Inbox project, its members can read and edit your custom lists, synced
  settings (including which project is your Inbox) and Pro ledger, because the carrier is still
  "yours" by author. (c) **Suspected**, traced on mobile only: a member who knows a routine's id
  can add a second carrier with the same id and `shared: true`; `RoutineRepositoryImpl.kt:635`
  may pick it, and your ticks then go into their task.
- Fix: hide a marked task only when you created it or it is a routine shared with you; warn
  before sharing the Inbox (or move carriers to a project that cannot be shared); when two
  carriers share a routine id, prefer your own.

**S-6 (P2, Linux) Secrets are only obfuscated.** Verified.
- Evidence: `src/main/index.ts:634` pins Chromium's `basic` password store on every Linux
  system to avoid a keyring deadlock, so `safeStorage` uses a fixed key. That covers
  `auth.json` (session, refresh and API tokens), `ai-key.json` and the calendar passwords and
  OAuth refresh tokens. Settings says so for the sign-in token and for calendars
  (`SecretStorageNotice.tsx`, `CalendarFeeds.tsx:83`) but not in the Assistant section.
- Impact: anyone who gets a copy of `~/.config/vicu` (a backup, a synced folder) has the tokens.
- Fix: try the real keyring with a time limit and fall back to `basic`, or offer it as a
  setting; show the same notice next to the AI key.

### 4.3 Checked and sound

- **Notes and comments.** Desktop: DOMPurify with a strict tag and attribute list, links limited
  to http, https and mailto (`sanitize-html.ts`, `description-html.ts`); comments are decoded
  into text and attachment ids, never HTML; CSP is `default-src 'self'` with no remote images
  or scripts in all three windows. Mobile: no WebView for content, the same link rule, images
  only by id from your own server. Viewing a task never contacts another host.
- **Windows and IPC.** Sandboxed, context-isolated, no node integration; navigation and new
  windows are refused; all 220 handlers go through `handleTrusted`; preloads pass payloads only.
- **Sign-in and tokens.** Passwords are never stored. Desktop encrypts with the OS keychain on
  Windows and macOS, writes atomically with mode 600, revokes the backup token on sign-out and
  checks the OIDC state. Mobile uses Tink with a Keystore key and the iOS Keychain (this device
  only); backup rules exclude the database, token stores and AI key; release builds log no
  requests.
- **Browser extension.** Only `tabs` and `nativeMessaging`, no content scripts, fixed extension
  ids, the bridge only writes one JSON file, wrappers are quoted, no system Node needed.
- **Obsidian.** A note is written to only when you save a task with the link, and only the
  note still in front. The one issue is S-1.
- **Update checker.** Fetches one GitHub address, compares versions safely, opens the release
  page through the link allowlist, downloads and runs nothing. Mobile has no update checker.
- **Assistant.** The key lives in the main process (Tink or Keychain on mobile), is never
  logged, and Node's client does not follow redirects. Tools are read-only, every write is a
  card you accept, ids are checked against tasks you may change, answers are plain text, the
  prompt marks other people's tasks as data. Plain http to a remote provider is warned about.
  Speech models are pinned to a commit and checked by SHA-256. The open microphone stops when
  the app goes to the background and after the idle limit.
- **Child processes and calendars.** Every helper is started with an argument list and no
  shell; calendar links must be http or https, are read-only, capped at 15 MB and never echo a
  response; files are chosen in the main process's own dialog.

## 5. API connectivity and lost updates

### 5.1 Findings

**C-1 (P2, desktop) A web page with status 200 counts as success.** Verified.
- Evidence: `src/main/api-client.ts:163-169`: a 2xx answer that is not JSON resolves as
  `{ success: true, data: null }`.
- Scenario: Vikunja sits behind a sign-in proxy (Authelia, Authentik, Cloudflare Access) whose
  session ran out. The proxy redirects to its login page, which answers 200 with HTML. A task
  edit is reported as saved, is not queued, and silently reverts at the next refresh. A list
  request throws instead (`paginate.ts:54` reads `items` of null), so the list fails without
  the offline fallback.
- Fix: treat a 2xx with a body that is not JSON as a failure with its own message ("the server
  answered with a web page: a sign-in proxy may need you to sign in"), and make it queueable
  for changes.

**C-2 (P2, desktop) One refused change blocks the queue for good.** Verified.
- Evidence: `src/main/offline/classify.ts:43`: any 403 on a task change stops the replay as an
  auth problem. `SyncPanel.tsx:165` then asks you to sign in again; only failed changes can be
  discarded, not waiting ones.
- Scenario: you edit a task of a shared project while offline; meanwhile the owner makes you
  read-only. Back online the edit gets 403. Every later queued change waits behind it, signing
  in again changes nothing, and there is no button to drop it. Mobile marks the same change
  failed and carries on.
- Fix: a 403 with a working session (the token still reads projects, the check
  `collabResult` already makes) moves the change to the failed log as "no write access".

**C-3 (P2, both) A repeating task can skip an occurrence.** Verified in both queues.
- Evidence: a completion is `{ done: true }` and nothing else (`TaskRepositoryImpl.kt:1244`,
  desktop `merge-patches` and replay); neither replay looks at the due date first. Vikunja
  moves a repeating task on from whatever date it holds when the patch arrives.
- Scenario: you tick "Take pills" on the phone while it is offline, or from a notification on a
  stale cache, and tick it on the desktop too. The second patch moves it on again and
  tomorrow's occurrence is gone.
- Fix: keep the due date that was completed in the queued change; at replay, send it only when
  the server's due date still matches, else count it as done. Add the rule to the contract.

**C-4 (P2, mobile) A passing refresh failure ends the session.** Verified in code.
- Evidence: `KtorClientFactory.kt:215-232`: after a 401, when the refresh fails, the fallback
  asks `getBestToken()`, which returns the same JWT as long as the phone's clock says it is
  valid (`AuthManager.kt:253`), so the backup token is never tried and `setNeedsReAuth()` runs.
- Scenario: the phone's clock is a few minutes slow, the server refuses the JWT, and the
  refresh request times out or gets a 503. You land on Setup with the queue paused. Restarting
  the app "fixes" it, because start-up does fall back to the backup token.
- Fix: in the fallback, use the stored API token whenever it differs from the refused one, and
  end the session only when the refresh itself was refused.

**C-5 (P2, both) Notes: the last save wins, unseen.** Verified on desktop.
- Evidence: a notes edit sends the whole `description`. A queued patch is replayed as stored,
  however old (`SyncEngine.kt:692`, desktop `replay.ts:213`), and the contract has a conflict
  rule only for carriers. On desktop, `TaskRow.tsx:512-514` replaces the text in an open card
  whenever the task's notes change in the cache.
- Scenarios: (a) two people add a line to the same task's notes; the later save removes the
  other line. (b) You type notes in an open card on the desktop; a refresh brings in someone
  else's change and your unsaved text is replaced. (c) A phone that was offline for two days
  replays an old due date over a newer one.
- Fix: send notes edits as a JSON Patch with a `test` of the notes that were read, the way
  routine carriers already do; on a 422, keep both versions and say so. Do not reset an editor
  that has unsaved text. Store the task's `updated` with a queued change and write the rule
  for older-versus-newer into the contract.

### 5.3 Checked and sound

- Both apps send only changed fields, built from the stored task at the moment of the write
  (swipes, bulk actions, widgets, notification actions, Ask, drags).
- Task writes go out one at a time in both apps, so SQLite's "database is locked" cannot lose
  a bulk change. One sync at a time on mobile.
- A 304 on a no-op patch is a success everywhere it matters. `per_page` never exceeds 1,000 and
  paging ends on `total_pages`.
- Offline queues fold create, edit and delete, remap temporary ids (also in relations, labels,
  comments and the Pro ledger), keep the queue on auth, 5xx and 429, and survive sign-in again
  and "Clear cache"; discarding asks first.
- Synced documents merge by hybrid-clock revision with a read-back; routine carriers use
  test-and-retry with a verify read.
- Desktop pins the token to the configured server and retries a stopped replay after 5 s, 15 s,
  then every minute.

## 6. Experience and consistency

- **E-1 (P2, desktop)** A waiting change cannot be discarded, only a failed one (see C-2).
  Mobile offers both.
- **E-2 (P3)** What "offline" covers differs: on mobile every edit is queued; on desktop
  project, label, section and order changes fail with a toast (D-SYNC-6).
- **E-3 (P3, mobile)** Small rollbacks are missing: a refused reorder keeps the new order on
  screen (`TaskRepositoryImpl.kt:230`), a refused label delete removes the label until the next
  refresh, a refused change holds its task still for 14 days (A-SYNC-3).
- **E-4 (P3)** Search (X-9), the Logbook's retention setting (X-10) and snooze (X-17) differ
  between the apps.
- **E-5 (P3, Linux)** The storage warning is shown for sign-in and calendars but not for the AI
